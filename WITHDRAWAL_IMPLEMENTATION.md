# Volunteer withdrawal

1. **Inspected:** volunteer dashboard and availability screens; volunteer activities, explore, request details and routes; elderly request details; caregiver request details and monitoring; `requestService`, `volunteerDashboardService`, `volunteerAvailabilityService`, `requestMatchingService`, `notificationService`, `caregiverLinkService`, `chatService`; request, volunteer and notification types; navigation, Firestore rules, existing acceptance tests and project instructions. Scheduling and assignment operations live in `requestService`; there are no separate schedule/assignment services.
2. **Existing logic:** acceptance already uses a transaction and one assignment document per request. Elderly cancellation retains the assignment as cancelled. No volunteer withdrawal existed. Reused this lifecycle and the notification collection/service.
3. **Modified:** `firestore.rules`, `src/app/(volunteer)/request-details/[id].tsx`, `src/services/requestService.ts`, `src/services/notificationService.ts`, `src/services/requestAcceptance.test.ts`, `src/types/notification.ts`, `src/types/volunteer.ts`.
4. **Created:** this report and `scripts/test-withdrawal-rules.cjs`.
5. **Eligible statuses:** accepted and scheduled, for the authenticated assigned volunteer only. In-progress, completed, cancelled and pending requests are rejected. The transaction rechecks current state after competing writes.
6. **Transition:** accepted/scheduled → pending on the same request document. Ownership and request content remain intact. Existing centralized pending label is “Looking for a volunteer.”
7. **Assignment:** clear assigned volunteer and denormalized profile fields; mark the assignment withdrawn. A later acceptance may replace that withdrawn assignment. Upcoming activities and dashboard already reload on focus; success navigates to activities.
8. **Schedule:** retain the requested date/time; clear acceptance and elder confirmation timestamps. The old assignment's date is historical, and its withdrawn status excludes it from active schedules. No standalone schedule records exist.
9. **History:** each withdrawal writes an immutable snapshot to `requestAssignmentHistory` before the assignment can be reused. No optional private reason is collected.
10. **Elderly notification:** “Volunteer Withdrew,” with activity-specific wording, written in the withdrawal transaction.
11. **Caregiver notification:** “Volunteer Withdrawal” uses the request's existing caregiver ID. Rules additionally verify the current accepted link through the elderly profile. Notifications, history, request and assignment commit together or not at all.
12. **Browse:** pending and unassigned requests return to the existing browse query without duplication.
13. **Matching/availability:** existing future-date, availability and interest filters apply unchanged. Past dates do not qualify for future matching. Acceptance does not consume availability slots, so withdrawal creates/restores none.
14. **Security:** added constrained withdrawal, immutable history, withdrawn-assignment replacement and notification permissions. Request ownership/content cannot change; request-only withdrawal is denied. Existing chat authorization revokes access for the withdrawn volunteer.
15. **Validation:** TypeScript and targeted ESLint checks passed. Nine withdrawal service tests passed (accepted/scheduled, disallowed statuses, identity, duplicate concurrency, start race, history, notification contents, browse and reassignment). Matching tests passed. The combined acceptance/matching run had 44 passes and one existing caregiver-history ordering failure; the unchanged function sorts by createdAt while the test expects terminal timestamps. Local Firestore emulator checks passed for accepted/scheduled withdrawal, atomic assignment enforcement, notifications/history, reassignment, duplicate rejection, prohibited statuses, wrong roles and ownership tampering. No device UI or real-project restart test was performed.
16. **Remaining checks/limitations:** deploy the rules with the app and smoke-test on device. The existing caregiver-history ordering failure remains. An inconsistent/stale caregiver ID causes the atomic write to fail safely rather than notify an unrelated person; existing request creation/link denormalization is unchanged. Existing request-keyed chat rooms are not migrated for replacement volunteers, so a room created for the previous volunteer needs a separate chat lifecycle update before the replacement can use it. Existing deterministic acceptance notifications may also need event-specific IDs for repeated acceptances; withdrawal notifications already use a unique transaction event ID.
