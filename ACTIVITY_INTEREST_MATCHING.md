# Volunteer activity-interest matching

1. **Files inspected:** volunteer profile, explore, request details and tab layout; volunteer dashboard and availability screen; `RequestFilterModal`; request, user, availability, dashboard and matching services; request and volunteer types; authentication profile setup; Firestore profile rules; existing matching and acceptance tests. Project instructions and the required Expo 57 documentation were also reviewed.
2. **Existing interest field:** `preferredActivityTypes` already existed on availability records, describing individual slots. There was no profile-wide interest editor or stored interest model. The profile now uses the same field name; slot preferences remain separate and are not silently imported as permanent interests.
3. **Activity source:** `REQUEST_ACTIVITY_TYPES` in `src/types/request.ts` is the request creation/filter source. `VOLUNTEER_ACTIVITY_TYPES` now references it directly, so profile and availability choices use the exact request values, including Appointment Companionship and Other. Unknown legacy labels are not guessed or remapped to different activities.
4. **Existing matching:** extended `requestMatchingService.ts`, which already matches full request durations against availability windows. No separate recommendation service was created.
5. **Created files:** `src/services/volunteerInterests.test.ts` and this report.
6. **Modified files:** `src/app/(volunteer)/profile.tsx`, `explore.tsx`, `request-details/[id].tsx`; `src/services/userService.ts`, `requestMatchingService.ts`, `requestMatchingService.test.ts`; `src/types/request.ts`, `volunteer.ts`.
7. **Storage:** `volunteerProfiles/{uid}.preferredActivityTypes`, saved with a server timestamp and merge semantics through the existing user service. Saving preserves verification/bio fields, permits clearing all selections, checks authenticated identity and volunteer role, and creates the profile document if absent. Existing owner-scoped profile rules already permit this; rules were not changed.
8. **Match rule:** only pending, unassigned requests can match. Canonical request activity must equal one of the saved interests after whitespace/case normalization. Unsupported values are ignored. No personal elderly/caregiver information is used.
9. **Browse:** Matches Your Interests appears first, followed by Other Available Requests. Cards retain all existing details and show separate interest and availability badges. With no interests, the existing availability-first order remains. Each request ID appears once. The existing future-request browse restriction remains.
10. **Manual filters:** temporary activity, date, location, duration and availability filters run before ranking. They never overwrite saved interests and can show activities outside those interests. No redundant quick filter was added.
11. **Availability:** priority is both matches, interest only, availability only, then other. Availability matching itself remains time-based. No AI score or additional matching collection was introduced.
12. **UI states:** profile provides accessible multi-select controls, selection marks, Save Interests, saving feedback, loading and retry states. Browse offers Set Interests when none are saved and View All Requests when no interests match. Interest-loading failures show a friendly retry message while allowing browsing/acceptance. Screens wait for their reads before showing match results and reload on focus, including after editing interests or accepting a request. No live browse listener existed, so this retains focus/explicit refresh behavior.
13. **Acceptance:** the existing acceptance transaction, assignments, notifications and upcoming activities are reused unchanged. Details show a positive interest-match indicator only for available matches; nonmatching interests do not block acceptance. Accepted requests are excluded from matching and the next browse load.
14. **Tests performed:** `npx tsc --noEmit`, targeted ESLint, and `git diff --check` passed. Matching/preference suites: 20 passed. Targeted existing acceptance/reload tests: 2 passed (37 unrelated tests intentionally skipped in that run). Coverage includes single/multiple/no interests, normalization, unavailable/assigned requests, ranking/deduplication, edited interests, manual and availability filters, canonical persistence, clearing interests, preserving profile fields, rejected identity/role and load failures. Persistence tests use a mocked Firestore; no real-project writes were made.
15. **Remaining TODOs:** device smoke-test Profile → Save Interests → Explore → Details → Accept, including returning to Explore and empty/error states. No new dependency, migration, rule deployment or navigation route is required. This task did not rerun the whole repository suite or the emulator; the earlier unrelated caregiver-history ordering issue remains outside this change.
